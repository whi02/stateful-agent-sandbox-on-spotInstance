# Crab: Agent 샌드박스를 위한 Checkpoint/Restore 런타임 (arXiv 2026)

## 한 줄 요약

AI 에이전트가 명령을 실행하는 샌드박스(컨테이너·microVM)의 상태를 언제, 얼마나 저장할지를 OS 수준에서 자동으로 판단하는 런타임입니다. **Spot 실행을 만든 이유 중 하나로 명시**했습니다. 대화 기록만 복구하면 작업의 8~13%만 성공하지만 Crab은 100% 복구했고, 장애가 없을 때 대비 실행 시간 증가는 1.9% 이내였습니다. 단, Spot 실험은 실제 AWS 회수가 아니라 **60초 알림을 무작위로 주입한 시뮬레이션**입니다.

## 풀려는 문제

- 코딩 에이전트(Claude Code, Codex 등)는 샌드박스 안에서 파일을 고치고, 패키지를 설치하고, 백그라운드 프로세스를 띄웁니다. 그래서 에이전트의 상태는 **대화 기록 + 파일시스템 + 살아 있는 프로세스**입니다.
- C/R(Checkpoint/Restore)이 필요한 경우: 장애 복구, **Spot/선점형 실행**, 강화학습 롤아웃 분기, 잘못된 행동의 롤백
- 기존 방식은 두 극단입니다.

| 방식 | 계층 | 저장하는 상태 | 정확성 | 비용 |
|---|---|---|---|---|
| Claude Code rewind | 앱 | 대화 + Git/파일 | 불완전 | 낮음 |
| LangGraph | 프레임워크 | 대화 | 불완전 | 낮음 |
| Docker | OS | 컨테이너 전체 | 정확 | 중간 |
| E2B (Firecracker) | VM | VM 전체 | 정확 | 높음 (스냅샷에 4초 이상) |
| Crab | 계층 횡단 | 필요한 만큼 | 정확 | 낮음 |

- 원인은 **agent–OS semantic gap**입니다. 에이전트 프레임워크는 도구 호출은 알지만 그 OS 영향을 모르고, OS는 상태 변화는 알지만 어느 턴이 복구에 중요한지 모릅니다.
- 실제로는 **75% 이상의 턴이 복구에 필요한 상태를 만들지 않습니다.** 모든 턴을 저장하는 것은 낭비입니다.

## 측정으로 확인한 문제 (3장)

- Terminal-Bench 50개 작업에 장애를 1번 주입했을 때
  - 처음부터 재시작: 100% 성공, 중앙값 시간 1.81배(재생) / 1.55배(실제 LLM)
  - 대화 + 파일시스템 복구: 48%(재생) / 34%(실제 LLM)
  - **대화만 복구: 6%(재생) / 28%(실제 LLM)**
- 턴 길이 중앙값 3.34초, 작업당 평균 117턴입니다. 호스트당 샌드박스 100개면 체크포인트 요청이 중앙값 초당 17건, p90 초당 26건입니다.
- ZFS 파일시스템 스냅샷은 동시성이 높아도 22ms 이내입니다. 반면 **CRIU 프로세스 체크포인트는 메모리 크기에 비례해 늘어**, 동시성이 높을 때 128MB 7.8초 ~ 1GB 47.4초까지 걸렸습니다.

## 설계

| 구성 요소 | 하는 일 |
|---|---|
| Coordinator | 에이전트와 LLM 사이의 프록시입니다. 턴 경계를 찾고, **LLM 응답을 기다리는 시간에 체크포인트를 겹쳐 실행**해 비용을 숨깁니다 |
| Inspector (eBPF) | 턴마다 OS에 보이는 변화(파일, 프로세스, 메모리)를 보고 "저장 안 함 / 파일만 / 프로세스만 / 전체" 중 하나로 분류합니다 |
| C/R Engine | 같은 호스트의 여러 샌드박스 체크포인트를 스케줄링합니다. 백엔드는 runc, ZFS 스냅샷, CRIU입니다 |

에이전트와 C/R 백엔드는 수정하지 않습니다.

## 실험 조건

- 호스트: AWS `c6id.32xlarge`(코어 128개, 메모리 256GB, NVMe 1.7TB × 4) **1대**
- 백엔드: runc-CRIU v1.3.4, OpenZFS v2.4.1
- 에이전트: Claude Code, iFlow-cli(Terminal-Bench), SWE-agent(SWE-bench). 각 벤치마크에서 장애 없이 풀리는 작업 100개를 뽑았습니다.

## 핵심 결과

| 항목 | 값 |
|---|---|
| 복구 정확도 | Crab 100%, 대화만 8~13%, 대화+파일 28~42% (Terminal-Bench) |
| 작업당 장애 1회일 때 실행 시간 | 장애 없을 때 대비 1.9% 이내 |
| 처음부터 재시작 | 최대 1.67배 (SWE-Bench) |
| 매 턴 전체 체크포인트 | 최대 3.78배 (샌드박스 96개, I/O 경합) |
| 저장이 필요 없다고 분류한 턴 | 최대 87% |
| 체크포인트로 드러난 지연 p95 | 작업 시간의 0.44% (샌드박스 64개, 장애 없음) |
| 롤백 도구 제공 시 | 실행 시간 최대 29%, 롤백 토큰 36% 감소 |
| 강화학습 롤아웃 | 롤아웃 토큰 40.0~64.2% 감소 |

### Spot 실행 실험 (7.5절)

- 샌드박스마다 **60초 사전 알림**으로 회수를 무작위 주입했습니다(실제 AWS 회수 아님, AWS 알림은 120초).
- 알림을 받으면 체크포인트를 만들고, 대체 인스턴스가 준비되면 복원합니다.
- **체크포인트+복원: 중앙값 0.71초, p95 1.00초.** 대체 인스턴스가 유예 시간 안에 준비되면 이전 비용이 완전히 가려집니다.
- 저장소를 대역폭 500MB/s인 공유 EBS로 제한하고, 호스트당 샌드박스 96개, 작업당 회수 1~5회로 압박했을 때 작업 완료 시간이 **중앙값 0.45~3.01%, p95 1.01~7.30%** 늘었습니다.

## 프로젝트에 주는 것

- **"stateful AI agent를 Spot에 올린다"는 아이디어를 직접 다룬 연구**입니다. 학계가 이 문제를 아직 열린 문제로 본다는 근거입니다.
- 에이전트 상태를 **대화 / 파일시스템 / 프로세스** 세 층으로 나누고, 대화만 살리면 대부분 실패한다는 수치를 줍니다. 상태 보존 범위를 정할 때 기준선이 됩니다.
- CRIU 체크포인트 시간이 메모리에 비례해 수십 초까지 늘어난다는 점은, AWS 2분 알림 안에 무엇을 저장할 수 있는지 계산할 때 쓰는 제약입니다.
- 실험 호스트가 CPU 인스턴스(c6id)입니다. 에이전트 샌드박스는 GPU가 아니라 CPU에서 돌고, LLM은 외부 API입니다.
  - (해석, 원문 아님) SkyServe의 측정(CPU Spot 확보 가능 시간 95.6~99.9%)과 합치면, 샌드박스형 에이전트는 GPU 서빙보다 Spot 확보가 쉬운 쪽일 가능성이 있습니다.
  - (해석, 원문 아님) 반대로 LLM을 외부 API로 부르면 Spot으로 줄일 수 있는 비용은 샌드박스 호스트 몫뿐입니다.

## 한계와 주의점

- **심사 전 arXiv v1**입니다.
- Spot 실험은 **시뮬레이션**입니다. 실제 회수, 대체 인스턴스 확보 실패, 여러 AZ 동시 회수는 다루지 않았습니다. 대체 인스턴스가 60초 안에 준비된다고 가정한 부분이 있습니다.
- 호스트 1대에서 실험했습니다.
- 비용 절감액(달러)은 측정하지 않았습니다.
- 사용자에게 보이는 지연(p95 응답 시간)이 아니라 작업 완료 시간으로 평가했습니다.

## 인용할 때 쓰는 표현

- "Crab(arXiv 2026, HKUST)에 따르면 에이전트 샌드박스를 대화 기록만으로 복구하면 Terminal-Bench 작업의 8~13%만 성공했고, 파일시스템과 프로세스 상태까지 복구한 Crab은 100%를 복구했다."
- "Crab의 Spot 실행 실험(60초 알림 시뮬레이션)에서 체크포인트와 복원은 중앙값 0.71초, p95 1.00초가 걸렸다."
