### Q1. 선생님이 말씀하신 AI Agent는 어떤 건지 (논문처럼 ML 파이프라인인지, 코딩 에이전트 실행 환경인지)

> ai agent 실행환경을 마이그레이션 하는거로 볼수도있겠고 마이그레이션을 잘되게 관리하는 ai agent가 될수도 있을듯

- 뜻 풀이 (해석, 원문 아님): "AI Agent"를 두 가지로 읽을 수 있다는 답입니다.
  - (가) **AI Agent의 실행 환경을 Spot으로 옮기는 것** — 우리가 정한 방향
  - (나) **마이그레이션이 잘 되도록 관리하는 AI Agent** — 에이전트가 Spot 운영(회수 감지, 이전 판단 등)을 돕는 쪽. CFP의 "Agent를 기능으로 붙이는" 방식에 가깝습니다.
- 영향: (가)는 선생님이 인정한 해석입니다. (나)는 선택지로 열려 있고, 하려면 실제 LLM 호출이 필요합니다.

### Q2. LLM을 호출하지 않고 실행 기록을 재생하는 방식에 대해 (어떻게 접근하실지, 실제 호출은 어느 정도)

> llm server까지 다룰 수 있으면 더 훌륭한 프로젝트가 되겠지만 난이도가 매우높으니 당장은 mcp tool실행환경이 스팟에서 운영되는관점에서 시작해보면 좋을듯

- 뜻 풀이 (해석, 원문 아님)
  - LLM 서버(모델 서빙)까지 Spot으로 다루면 더 좋지만 지금은 하지 않는 것이 좋다는 뜻입니다.
  - 시작점으로 **"MCP tool 실행환경이 Spot에서 운영되는 관점"**을 제시했습니다. MCP는 에이전트가 도구를 호출하는 표준 규격이고, "MCP tool 실행환경"은 그 도구가 실행되는 서버·샌드박스로 읽힙니다.
  - 재생 방식과 실제 모델 호출 정도에 대한 직접적인 의견은 없었습니다.
- MCP 스펙으로 확인한 것 ([MCP draft 스펙](https://modelcontextprotocol.io/specification/draft/server/tools), 2026-10-16 확인, draft라 바뀔 수 있음, documents 밖)
  - 도구 호출은 JSON-RPC `tools/call` 요청이고, 결과에 `isError`로 실행 오류를 알려 모델이 스스로 고치게 합니다.
  - 프로토콜에는 연결 단위 세션이 없습니다. 상태가 필요한 서버는 "상태 핸들"(예: `basket_id`)을 도구 결과로 돌려주고, 이후 호출마다 그 핸들을 인자로 받는 방식을 권장합니다. 서버가 상태를 핸들 이름으로 보관합니다.
  - 핸들이 만료되거나 모르는 핸들이면 도구 실행 오류를 돌려주어 모델이 새로 만들게 합니다.
- (해석, 원문 아님) Spot과 연결하면, MCP 도구 서버가 회수되었을 때 핸들이 가리키던 상태(열려 있던 셸 세션, 작업 파일 등)가 사라지면 핸들이 만료됩니다. 상태를 보존해 두면 같은 핸들로 이어서 쓸 수 있습니다. 이것이 "상태 보존 수준별 비교"와 직접 이어집니다.
- 아직 모릅니다: "MCP tool 실행환경"이 (a) 에이전트가 호출하는 MCP 서버 전체인지, (b) 코드·셸을 실행하는 도구의 실행 환경(샌드박스)인지는 말씀하지 않았습니다. 후속 질문 후보입니다 (5절).

### Q3. 인스턴스 선택에 SPS 같은 가용성 신호를 같이 보려는 것에 대해

> sps같은 가용성 신호를 분석한 논문 도 매우 많긴하지만, 난이도가 매우높으니 당장은 워크로드를 판별해서 요구하는 사양중 가장 안정적일거같은걸로 선택하는게 좋을듯

- 뜻 풀이 (해석, 원문 아님)
  - 가용성 신호를 **분석하는** 연구(예측, 조기 경보 등)는 지금 하지 않는 것이 좋다는 뜻입니다.
  - 대신 워크로드를 보고 필요한 사양을 정한 다음, 그 사양을 만족하는 인스턴스 중 가장 안정적일 것 같은 것을 고르는 단순한 방식을 제안했습니다.
  - "안정적"을 무엇으로 판단할지는 말씀하지 않았습니다. AWS가 이미 제공하는 값(Spot Instance Advisor 회수 빈도 구간, SPS 조회값)을 조회해서 비교하는 정도로 읽을 수 있지만 확인하지 못했습니다.
