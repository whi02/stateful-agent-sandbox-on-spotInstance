## 초록

Spot 인스턴스는 클라우드의 남는 자원을 크게 할인된 가격에 쓸 수 있게 해 준다. 클라우드 업체가 가용성 정보를 제공하고 있지만, Spotlake 같은 기존 도구는 **단일 노드 기준** 가용성 데이터만 제공한다. 이는 여러 노드를 쓰는 최근의 분산 애플리케이션에는 부족하다.

이 논문은 단일 노드 가용성 데이터의 한계를 보여 주고, **다중 노드 가용성 데이터를 수집하는 시스템**을 소개한다. 수집한 데이터를 분석했고, Spotlake를 확장해 이 다중 노드 데이터를 누구나 쓸 수 있게 공개했다.

**키워드**: 클라우드 컴퓨팅, Spot 인스턴스, Spot 인스턴스 데이터셋

## 1. 서론

**Spot 인스턴스와 가용성 정보.** Spot 인스턴스는 클라우드 업체가 쓰지 않는 자원을 최대 90%까지 할인해 제공하는 서비스다. AWS, Azure, GCP, Alibaba, IBM 등 주요 업체 대부분이 제공한다. Spot 가격은 계속 바뀌고 회수(interrupt)도 일어나기 때문에, 사용자에게는 비용 절감과 안정성이 중요한 고려 사항이다. 이를 돕기 위해 업체들은 Spot 가격과 가용성 데이터를 제공한다. 예를 들어 AWS는 지난 한 달간의 회수 비율과 실시간 가용성 데이터인 **AWS Spot Placement Score(SPS)**를 제공한다.

**SPS의 한계와 Spotlake.** SPS는 Spot 인스턴스를 지금 바로 확보할 수 있는지를 나타내지만, 내부 계산 방식은 공개하지 않는다. 콘솔이나 API로 조회할 수 있지만 조회 횟수 제한이 크다. 이 제한을 극복하고 데이터에 쉽게 접근할 수 있도록 **Spotlake**라는 웹 서비스가 제안되었다.

**다중 노드 정보가 필요한 이유.** 최근의 클라우드 애플리케이션은 GPU를 단 여러 노드로 구성한 분산 환경이나 대규모 컴퓨팅 자원을 자주 필요로 하고, 둘 다 비용이 크다. 이 비용을 줄이려고 여러 노드를 Spot으로 쓰는 경우가 늘고 있어서, 다중 노드 Spot 가용성 정보의 필요성도 커지고 있다. 그러나 Spotlake는 단일 노드 Spot 인스턴스의 SPS만 제공하고, 여러 인스턴스를 동시에 요청하는 경우의 SPS는 제공하지 않는다.

**단일 노드 점수의 한계 실험.** 이 논문은 단일 노드 가용성 점수의 한계를 살펴보고 해결책을 제안한다. 단일 노드 SPS가 다중 노드 요청의 가용성을 반영하는지 확인하려고, SPS가 최고점인 3인 instance type 32개를 무작위로 골라 요청하는 인스턴스 수를 늘려 가며 성공률을 측정했다. 그림 1처럼 성공률은 **1대일 때 100%에서 50대일 때 20%로 급격히 떨어졌다.** 따라서 단일 노드 SPS는 다중 노드를 확보할 수 있는지 판단하는 믿을 만한 지표가 아니다.

**이 논문의 기여.** 이 한계를 해결하려고 다중 노드 가용성 데이터 수집 시스템을 제안하고 수집한 데이터를 자세히 분석했다. 또 Spotlake 플랫폼에 다중 노드 가용성 점수를 통합해 웹 서비스로 공개했다([spotlake.ddps.cloud](https://spotlake.ddps.cloud/)). 이를 통해 사용자가 클라우드에서 대규모 분산 애플리케이션을 운영할 때 비용 효율적이고 믿을 만한 결정을 내릴 수 있다.

### 그림 1

**단일 노드 가용성 점수가 높은 type에 대해, 요청 노드 수를 바꿔 가며 요청했을 때 실제로 확보된 비율**

- 가로축: 요청한 노드 수 (1~50)
- 세로축: 요청 충족 비율 (0.0~1.0)
- 막대가 1대에서 1.0으로 시작해 노드 수가 늘수록 낮아지고, 50대 부근에서 약 0.2까지 떨어진다.

## 2. 구현과 데이터 분석

### 구현

- **수집 주기:** 10분마다 조회했고, 여러 목표 노드 수에 대해 데이터를 모았다.
- **가격 데이터:** AWS가 제공하는 가격 데이터셋을 그대로 사용했다.
- **저장:** 수집한 데이터는 S3에 저장되어 사용자가 직접 접근할 수 있다.
- **파일 이름:** 과거 데이터까지 남기려고 "연-월-일-시각" 규칙으로 저장한다.

### 데이터 분석

분석한 다중 노드 SPS 데이터셋의 범위는 다음과 같다.
- **기간:** 2024년 7월 1일 ~ 2025년 1월 15일
- **대상:** 17개 리전, 서로 다른 instance type 844개

**그림 2: 범주별 SPS 변화.**
- **축과 선:** 가로축은 목표 용량(요청 대수), 세로축은 평균 SPS이고, 선 하나가 instance 범주 하나다.
- **결과:** 요청 용량이 커질수록 SPS가 대체로 낮아진다. 즉 큰 요청일수록 가용성이 낮다.
- **범주별 차이:** **Accelerated Computing(GPU 계열)이 가장 가파르게 떨어진다.** GPU 인스턴스 수요가 높기 때문으로 보인다. 다른 범주도 정도 차이는 있지만 모두 낮아진다.
- **의미:** 대규모 자원 풀을 구성할 때는 알맞은 instance type을 고르는 것이 중요하다.

**그림 3: 출시 연도와 SPS의 관계.**
- **축과 하위 그래프:** 가로축은 instance type의 출시 연도, 세로축은 평균 SPS다. 하위 그래프는 목표 노드 수(1대, 25대, 50대)별로 나뉘고, 그 안에서 범주별로 묶었다.
- **대부분 범주:** **최신 instance type일수록 SPS가 낮은** 경향이 있고, 목표 노드 수가 많을수록 이 경향이 강해진다(그림 3b, 3c).
- **GPU 계열은 반대:** Accelerated Computing 범주는 최신 type일수록 SPS가 높다. NVIDIA H100 GPU를 단 p5.48xlarge가 높은 가용성을 보였다.
- **원인 추정:** SPS 계산 방식이 공개되지 않아 정확한 원인은 알 수 없다. 논문이 제시하는 가능한 설명은 두 가지다.
  - CPU 기반 인스턴스는 GPU보다 소프트웨어 의존성이 적어 최신 type으로 옮기기 쉽고, 그래서 최신 CPU type에 수요가 몰린다.
  - 최신 GPU 인스턴스는 가격이 높아 사용이 제한되고, 그래서 SPS가 높게 나온다.

### 그림 2 · 그림 3 축 정보

|---|---|---|---|

| 그림 3: 범주별 SPS의 시간에 따른 변화 | 출시 연도 (2015~2023) | SPS (1.00~3.00) | (a) 목표 노드 1대, (b) 25대, (c) 50대 |

## 3. 결론

다중 노드 환경에서 단일 노드 가용성 점수 데이터가 갖는 한계를 다루고, 다중 노드 가용성 데이터 수집 시스템을 제안했다. 다만 현재 시스템은 AWS Spot 인스턴스만 지원하므로, 앞으로 Microsoft Azure 같은 다른 클라우드 업체로 확장해야 한다.

## 정리하면서 붙인 메모 (원문에 없는 내용)

- **용어**
  - **SPS (Spot Placement Score):** AWS가 제공하는, Spot 용량을 확보할 가능성을 나타내는 점수입니다.
  - **목표 용량(Target Capacity):** 한 번에 요청하는 인스턴스 수입니다.
  - **Spotlake:** 논문 저자 그룹이 운영하는 Spot 데이터 공개 서비스입니다.
- **점수 범위 차이:** AWS 공식 문서([Spot placement score](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/spot-best-practices.html))는 SPS를 **1~10점**이라고 설명합니다. 그런데 이 논문은 최고점을 **3**으로 쓰고 그래프 축도 1~3입니다. 왜 다른지는 논문에 설명이 없어서 확인하지 못했습니다.
